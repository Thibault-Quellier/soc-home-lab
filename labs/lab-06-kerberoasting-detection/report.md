# Lab 06 – Kerberoasting Detection

## 1. Executive Summary

This lab demonstrates how Kerberos Service Ticket (TGS) requests can be monitored in an Active Directory environment to support the detection of Kerberoasting activity.
A dedicated service account (`svc_sql`) was configured with a Service Principal Name (SPN). A Kerberos TGS request was generated from a domain workstation using native Windows functionality, producing Windows Security Event ID 4769 on the Domain Controller.

The generated telemetry was validated locally through Windows Event Viewer. Wazuh collected Kerberos-related Event ID 4769 activity; however, the specific event generated during the simulation did not trigger a dedicated alert under the default ruleset. During the investigation, it was observed that the Windows Security event was successfully generated on the Domain Controller, while the corresponding event was not converted into a Wazuh alert under the default ruleset. This highlights the importance of validating detections both at the log source and within the SIEM pipeline.

**MITRE ATT&CK**

- **T1558.003 – Kerberoasting**
- **TA0006 – Credential Access**
  
## 2. Lab Objectives

The objectives of this lab were to:

- Understand how Kerberos Service Ticket (TGS) requests are generated in an Active Directory environment.
- Configure a dedicated service account with a valid Service Principal Name (SPN).
- Generate Windows Security Event ID 4769 using native Windows authentication.
- Validate Kerberos-related telemetry on the Domain Controller.
- Verify event collection and visibility within the Wazuh SIEM.
- Understand the differences between Windows event generation and SIEM alert generation.
- Map the observed activity to the MITRE ATT&CK framework (T1558.003 – Kerberoasting).

## 4. Lab Preparation

Before generating Kerberos authentication events, the Active Directory environment was prepared to simulate a realistic service account commonly targeted during Kerberoasting attacks.
The following preparation steps were completed:

1. Verified that the Active Directory Domain Services (AD DS) role was operational.
2. Created a dedicated service account named `svc_sql`.
3. Registered the following Service Principal Name (SPN) to the service account:

   ```
   MSSQLSvc/DC01.soc.local:1433
   ```

4. Verified the SPN registration using:

   ```powershell
   setspn -L svc_sql
   ```

5. Confirmed that Windows Security auditing was enabled and that Event ID **4769 (Kerberos Service Ticket Operations)** was being generated by the Domain Controller.
This configuration provided a realistic Active Directory environment for monitoring Kerberos TGS requests without using offensive tooling.

## 5. Kerberos TGS Request Generation

To generate a Kerberos Service Ticket (TGS) request, a standard domain user (`user-low`) requested a service ticket for the registered SQL Service Principal Name (SPN) using native Windows functionality.
The following command was executed from the Windows client:

```cmd
klist get MSSQLSvc/DC01.soc.local:1433
```

The request generated a Kerberos TGS request handled by the Domain Controller.
As expected, Windows Security **Event ID 4769 (A Kerberos service ticket was requested)** was generated on the Domain Controller.
The generated event contained the following relevant information:

- Requesting account: `user-low`
- Service account: `svc_sql`
- Registered SPN: `MSSQLSvc/DC01.soc.local:1433`
- Event ID: **4769**
- Result: **Success**
- Kerberos ticket encryption recorded by Windows

No offensive tools were used during this simulation. The objective was to generate legitimate Kerberos authentication telemetry suitable for SOC monitoring and detection.

## 6. Detection & Analysis

The generated Kerberos TGS request was successfully recorded by the Domain Controller as Windows Security **Event ID 4769**.
Analysis of the event confirmed:

- Successful Kerberos Service Ticket request.
- Request initiated by the standard domain user `user-low`.
- Service account targeted: `svc_sql`.
- Kerberos authentication completed successfully.
- Client IP address successfully identified.

The event was then investigated within Wazuh to validate SIEM telemetry.
Although Event ID **4769** was successfully collected by Wazuh, the specific Kerberos event generated during the simulation was not converted into an alert by the default Wazuh ruleset.
This investigation demonstrated an important SOC concept:

- Event generation on the monitored endpoint.
- Log collection by the SIEM.
- Alert generation are three independent stages.

An event may exist on the original Windows log source without necessarily generating a SIEM alert under the default detection rules.
This highlights the importance of validating both the original event source and the SIEM detection pipeline during security investigations.

## 8. Lessons Learned

This lab reinforced several important concepts related to Kerberos monitoring and SOC investigations.
Key takeaways include:

- Understanding how Service Principal Names (SPNs) enable Kerberos Service Ticket (TGS) requests.
- Identifying Windows Security Event ID 4769 as the primary event associated with Kerberos service ticket requests.
- Validating security events directly on the Domain Controller before relying on SIEM detections.
- Recognizing that event generation, log collection, and alert generation are independent stages within a monitoring pipeline.
- Understanding that default SIEM rulesets may not generate alerts for every collected security event.
- Appreciating the importance of investigating discrepancies between native Windows logs and SIEM telemetry during incident analysis.

This lab also demonstrated the value of validating the entire detection pipeline rather than assuming that all generated events will automatically produce security alerts.

## 9. Conclusion

This lab demonstrated how Kerberos Service Ticket requests can be generated, monitored, and analyzed within an Active Directory environment from a SOC perspective.
By configuring a dedicated service account with a valid Service Principal Name (SPN), generating a legitimate Kerberos TGS request, and analyzing Windows Security Event ID 4769, the complete detection workflow was successfully validated at the log source.
The investigation also highlighted an important operational consideration: successful event generation on a monitored system does not necessarily result in a corresponding SIEM alert under the default detection rules. This reinforces the importance of validating both native system logs and SIEM telemetry during security investigations.
This lab strengthens the understanding of Kerberos authentication monitoring and provides a solid foundation for future detection engineering and Active Directory threat hunting scenarios related to Kerberoasting (MITRE ATT&CK T1558.003).
